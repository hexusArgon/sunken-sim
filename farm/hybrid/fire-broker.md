# Fire packed compile broker — opt-in, not deployed

## Contract
`job.fire_compile_broker={"enabled":true,"backend":"dml"}` selects the native hybrid entry, one spawned job-owned compile owner, CPU-only persistent pool clients and unchanged native span scheduler. Omit the setting (default) for the existing path. `backend=cpu` is an explicit CPU-test reduction backend, never GPU parity. Only Fire is accepted. Require CPU exact selection, CPU canonical final path and scalar planner; no other spec changes.

Parent and clients never call device detection or `torch_directml.device`. The SAME single owner serves 8 actual preflight inputs and subsequent workers, so no extra preflight owner survives. Worker self-check remains active. Hardware admission is still a deployment decision: another job's GPU contexts are not accounted by a per-job service. Do NOT enable alongside the resident six-owner Fire.

## Transport and bounds
One outstanding synchronous call/client, request identity `(job generation,client slot,sequence)`, independent bounded reply queues, stale reply rejection, monotonically accepted sequences. Shared FIFO has N slots. Byte credits reserve whole requests under one lock, before enqueue, with deadlines (no partial-credit deadlock). Pending coalescing is count-bounded; total transmitted payload is credit-bounded. Exact shape/dtype/sorted-field compatibility buckets, contiguous concat preserving request and row order; heterogeneous widths/execution counts stay separate. No sorting by score or event clock. No event clipping.

Defaults:512broker rows;8MiB raw/serialized request cap;64MiB in-flight payload credits;128MiB padded graph estimate;32MiB reusable input tensors;8MiB/client compile-result cache (and separate8MiB CPU-exact score cache);10ms coalescing;30s request/startup deadline;5s owner drain. Per-client source arrays/serialization temporaries, NumPy concatenate, Python/IPC allocator overhead and driver graph caches are additional, not asserted within the payload caps. Input tensor payload cap is not total VRAM. Owner shutdown occurs after native pool drain; only its own Process handle may be terminated after bounded join. Hard owner exit sets the shared stopped flag via a parent sentinel watcher. Timeouts/errors replay exact CPU scoring locally; no logical span is counted twice merely because a pure compile was attempted.

## What is new vs existing
Existing `finish_many`, `chunked_many`, batched talent/glyph and lockstep ESC search are REUSED, not re-invented. The existing bare-top10 category gate still admits before ANY refinement. Broker transport coalesces those prepared reduction requests across CPU workers, reducing kernel/transfer boundary count when compatible traffic overlaps. Existing immutable TapeLRU and canonical compile cache continue to reuse only verified cadence/source contexts; they already removed CPU timeline/exact compile work. New full-payload compile-result reuse avoids repeat transfers and reductions; CPU score remains per-build/context correct. `exact_score_cache=true` (default false) enables optional client exact-score memoization seeds the SAME existing canonical guard only with previously CPU-exact values and complete stats/build/events/verified-source context; no winner/tie guard is disabled. Overflow/unknown keys fail closed to normal exact computation.

No new GPU event scheduler, no Fire physics changes, no global resource allocator, no GPU utilization target, no speed claim. No attempt to cache arbitrary final DPS by gear alone, mutate pressure histories, truncate events or reuse tensors after an asynchronous result is still outstanding. The single service materializes D2H before buffer reuse. Existing DevicePool is now owner-wide instead of one pool per GPU worker; intermediate GPU graph allocations remain backend-managed (not all intermediates were made persistent).

## Profile semantics
CPU pack, caller serialization, IPC roundtrip, owner queue/coalescing/merge, upload host submission, compile host submission, D2H+completion wait, CPU scoring, exact selection and residual timeline/other wall time are separate counters. Some are nested, not additive. D2H wait includes outstanding asynchronous GPU work; host submission timings are NOT device kernel durations. Observer failures never enter the math error path. Per-span deltas aggregate once, cached rows and completed logical chunks are distinct from newly compiled rows.

## Checkpoint/source policy
No resident Fire migration, metadata rewrite, resume or restart. New path persists explicit protocol+resource limits in checkpoint/result; mismatch raises rather than resetting progress. Generation is per service and intentionally not persisted. Original job identity, native spans, attributed admission observations and full winner payloads are retained on same-config resume. The normal source fingerprint changes because new source files and coordinator hooks exist; no generic bypass. Existing live processes retain imported c904359; the checkout previously bbc9da4 is a different fingerprint. For any future current-farm deployment request, separately back up/validate native signatures and obtain explicit authorization; this implementation must NOT be applied as a blind checkpoint migration.

## Verification before real deployment
Run matched actual DirectML baseline vs broker at equal CPU layout, actual top80 inputs, warm shared gate and representative expensive refinement/ring/Amp strata. Record startup/warm/drain, whole logical throughput, max/p95 waits, true device owners, fallback/replay counts, memory caps and exact CPU winners/payloads. No extra DML context while the current Fire owns six. CPU transport/CPU-device tests are necessary correctness evidence, not DML parity or acceleration evidence. Runtime GPU stage profile and actual1-owner hardware behavior remain deferred.

CPU profiling found full-context exact-score cache key construction expensive (1.30s in a two-chunk resume fixture with only1hit), so this experimental reuse stays separately OFF even inside the opt-in broker. Existing TapeLRU/compile-exact reuse remains active; no claimed speed benefit from the extra score cache. Enable it only after matched workload evidence.
